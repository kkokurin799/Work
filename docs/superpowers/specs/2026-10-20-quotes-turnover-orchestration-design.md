# Запуск расчета обращаемости сразу после завершения загрузки котировок

Дата: 2026-10-20
Статус: предложение к согласованию
Контур: Управление рыночными данными (Digital Q.FinMarkets)
Связанный диалог: загрузка истории при появлении бумаги в справочнике / входящем переводе ЦБ

## 1. Проблема

Сейчас нет сигнала «загрузка котировок по инструменту закончилась». Расчет обращаемости запускается спустя некоторое время после `initialPositionLoad` в надежде, что котировки уже лежат в базе.

Это ломается в рабочем сценарии:

1. Клиент купил бумагу у другого брокера и перевел ее к нам.
2. Бумаги не было в справочнике (редкий выпуск).
3. При добавлении в справочник нужна история обращаемости с даты размещения, а не только за вчера.
4. Вызываются два метода подряд: загрузка рыночных данных и расчет обращаемости.
5. Загрузка асинхронная, идет в два источника, еще и постранично. Второй метод стартует слишком рано.
6. Наружу нет статуса успех / пусто / ошибка. Нельзя ни дождаться результата, ни понять, что историю надо перезапросить.

Два источника усиливают разрыв:

| Что грузим | Источник |
|---|---|
| Котировки российских бумаг | RuData |
| Котировки иностранных бумаг | Cbonds |
| СЧА паев (российских и иностранных) | Cbonds |

Для российского пая часто нужны оба: котировки из RuData и СЧА из Cbonds. «RuData ответил 200» не значит, что можно считать обращаемость.

Глобального «окончания загрузки котировок» в системе и не должно быть. Котировки по уже известным ФИ догружаются каждый день, а новые бумаги появляются в течение дня. Единица готовности — не конец операционного дня, а конкретный инструмент и период.

Отдельно: у RuData есть витринный сервис «Обращаемость ценных бумаг» для НДФЛ. Это готовый флаг поставщика, он не закрывает иностранные бумаги и СЧА паев из Cbonds и не заменяет внутренний расчет по итогам торгов. Ниже речь про оркестрацию **собственного** расчета, а не про подмену его витриной RuData.

## 2. Цель

После появления бумаги в справочнике (и в ежедневном цикле по уже известным ФИ) расчет обращаемости должен стартовать **в тот же момент, когда по этому инструменту и периоду все нужные источники дошли до терминального статуса**, а не через фиксированную паузу.

Критерии успеха:

1. Для новой бумаги история запрашивается с даты размещения по текущую дату. Расчет не стартует, пока не завершена последняя страница загрузки по каждому требуемому источнику.
2. Вызывающая сторона получает `jobId` и конечный статус: успех, пусто (источник ответил, данных нет), ошибка, частичный отказ.
3. Ежедневное обновление идет тем же механизмом, только период = один торговый день.
4. Повторный вызов с тем же ключом не плодит вторую загрузку и второй расчет.
5. Отсутствие котировок по неликвиду — валидное завершение, а не вечное ожидание. Обращаемость все равно считается (результат: бумага не обращается).

## 3. Три варианта

### A. Оставить паузу / ночной батч

Как сейчас: `initialPositionLoad`, sleep или отложенный job, затем расчет.

Плюсы: почти ничего не делать.
Минусы: глубина истории и SLA RuData/Cbonds плавают; два источника независимы; нет статуса; редкая бумага, пришедшая днем, получает обращаемость с задержкой или с дырой.

Не подходит как целевое решение. Паузу можно оставить только как аварийный watchdog (см. ниже).

### B. Сделать `initialPositionLoad` синхронной сагой

API ждет оба источника, потом сам считает обращаемость и возвращает готовый результат.

Плюсы: для вызывающего кода «два метода подряд» остаются одним вызовом.
Минусы: история с даты размещения — минуты и постраничные запросы (у Cbonds лимит 1000 записей на ответ). HTTP/BPM-таймауты неизбежны. Ежедневный поток так не обслужишь. Загрузчики остаются без собственного контракта завершения.

Не подходит как основной контракт. Синхронным может быть только **прием заявки**.

### C. Задание на загрузку + барьер по источникам + событие готовности (рекомендуется)

Появление бумаги или ежедневный цикл создает `QuoteLoadJob` на `(instrumentId, from, to, mode)`.
Оркестратор по правилам маршрутизации открывает дочерние `SourceTask` (RuData и/или Cbonds).
Каждый загрузчик сам сообщает терминальный статус **после последней страницы**.
Когда все обязательные задачи терминальны, оркестратор публикует `QuotesReady` и сразу ставит `TurnoverCalcJob`.
Вызывающая сторона держит `jobId`: либо ждет событие, либо читает статус.

Плюсы: один механизм на историю и на день; два источника стыкуются явно; пустой ответ отличим от «еще грузится»; есть успех/ошибка; не нужен глобальный «конец загрузки».
Минусы: загрузчики должны эмитить завершение (сейчас этого нет — это и есть корневой пробел). Появляется реестр заданий.

**Рекомендация: C.** Корневая причина не в расчете обращаемости, а в отсутствии завершаемости загрузки. Пауза — попытка угадать то, что загрузчик обязан сообщить сам.

## 4. Ключевой принцип

> Готовность считается по заданию `(ФИ, период, набор источников)`, а не по системе в целом.

`initialPositionLoad` не «грузит рынок». Он **принимает заявку** на конкретную бумагу и период. Расчет обращаемости — следующий шаг той же заявки, его вызывает оркестратор, а не внешний код «через некоторое время».

Два сегодняшних последовательных вызова нужно разорвать на стороне клиента. Снаружи остается одна команда. Внутри: загрузка → барьер → расчет.

## 5. Маршрутизация источников

Правила задаются справочником, не хардкодом в вызывающем коде. Стартовый набор:

| Класс инструмента | Котировки | СЧА | Обязательные SourceTask |
|---|---|---|---|
| Российская акция / облигация / иное, не пай | RuData | нет | `RUDATA_QUOTES` |
| Иностранная бумага | Cbonds | нет | `CBONDS_QUOTES` |
| Российский пай | RuData | Cbonds | `RUDATA_QUOTES`, `CBONDS_NAV` |
| Иностранный пай | Cbonds | Cbonds | `CBONDS_QUOTES`, `CBONDS_NAV` |

Уточнение по российскому паю: если бумага не торгуется на бирже и котировок в RuData быть не должно, правило можно сузить до `CBONDS_NAV`. Это настройка маршрута, а не исключение из барьера.

Барьер закрывается, только когда **все обязательные** задачи задания в терминальном статусе.

## 6. Целевой поток

```text
Триггер
  ├─ бумага добавлена в справочник / входящий перевод
  └─ ежедневный цикл по известным ФИ
        │
        ▼
  QuoteLoadJob (instrumentId, from, to, mode)
        │
        ├─ SourceTask RuData   ──► страницы ──► SUCCEEDED | EMPTY | FAILED
        └─ SourceTask Cbonds   ──► страницы ──► SUCCEEDED | EMPTY | FAILED
        │
        ▼
  Join: все обязательные задачи терминальны?
        │
        ├─ да, нет FAILED ──► QuotesReady ──► TurnoverCalcJob ──► TurnoverReady
        ├─ да, есть FAILED ──► QuoteLoad FAILED, расчет не стартует, алерт, retry
        └─ нет ──► ждем; watchdog только если пробит SLA
```

### 6.1. Режимы задания

| mode | from | to | Когда |
|---|---|---|---|
| `INITIAL_HISTORY` | дата размещения | текущая дата (или дата входящего остатка) | новая ФИ в справочнике, входящий перевод редкой бумаги |
| `DAILY` | торговый день T | торговый день T | регламент по уже известным ФИ |

Один движок. Различается только период и триггер.

### 6.2. Что считается завершением загрузчика

Не HTTP 200 на старт и не «первая пачка записана».

Загрузчик закрывает `SourceTask`, когда выполнено одно из:

- все страницы периода записаны (`SUCCEEDED`);
- источник ответил, что данных за период нет (`EMPTY`) — для неликвида это норма;
- исчерпаны ретраи или источник недоступен (`FAILED`);
- бумага в этом источнике не найдена (`NOT_FOUND`) — терминально; для обязательного источника join трактует это как `FAILED` задания (скорее ошибка маршрута, чем пустой рынок).

Cbonds: лимит 1000 записей, нужен цикл по `offset`, пока `offset + length >= total`. RuData: аналогично, если API режет выдачу.

Пока задача в `RUNNING`, оркестратор **не имеет права** запускать расчет. Именно это чинит сегодняшний последовательный вызов двух методов.

### 6.3. Расчет обращаемости

Стартует только по `QuotesReady` того же `jobId`.

Вход: идентификатор ФИ, период, версия снимка котировок (чтобы расчет был воспроизводим).

Идемпотентность: повтор `QuotesReady` с тем же снимком не запускает второй расчет.

Если источник `EMPTY`, расчет все равно выполняется: обращаемость строится по имеющимся (нулевым) итогам торгов. Статус бумаги должен стать актуальным, а не остаться «еще грузится».

## 8. Автомат статусов

`QuoteLoadJob`:

```text
ACCEPTED
  → RUNNING          (первая SourceTask перешла в RUNNING)
  → QUOTES_READY     (все обязательные: SUCCEEDED | EMPTY; ни одной FAILED / NOT_FOUND)
  → CALC_RUNNING
  → COMPLETED        (обращаемость посчитана)
  → FAILED           (обязательный источник FAILED после ретраев, либо упал расчет)
  → CANCELLED
```

Допустимые переходы из `QUOTES_READY` только в `CALC_RUNNING` или `FAILED` (если постановка расчета не удалась — это тоже ошибка, ее видно).

Watchdog: если `RUNNING` дольше SLA (отдельно для `DAILY` и `INITIAL_HISTORY`), статус не меняем молча. Пишем `STALE` в мониторинг, эскалируем, не запускаем расчет «на всякий случай» — это вернет текущий баг.

## 9. Контракт API и события

Идея: вызывающий код больше не вызывает расчет. Он создает заявку и либо подписывается, либо читает статус.

### Команда (замена последовательных двух методов)

`POST /market-data/quote-load-jobs`

```json
{
  "instrumentId": "FI-...",
  "mode": "INITIAL_HISTORY",
  "periodFrom": "2019-03-12",
  "periodTo": "2026-10-20",
  "correlationId": "transfer-...",
  "reason": "INSTRUMENT_ADDED"
}
```

Ответ сразу, без ожидания источников:

```json
{
  "jobId": "qlj-...",
  "status": "ACCEPTED",
  "sources": ["RUDATA_QUOTES", "CBONDS_NAV"],
  "idempotencyKey": "FI-...|INITIAL_HISTORY|2019-03-12|2026-10-20"
}
```

`initialPositionLoad` либо становится фасадом этой команды, либо внутри создает тот же `QuoteLoadJob`. Внешнему процессу не нужно знать, RuData это или Cbonds.

### Статус

`GET /market-data/quote-load-jobs/{jobId}`

```json
{
  "jobId": "qlj-...",
  "instrumentId": "FI-...",
  "status": "COMPLETED",
  "sources": [
    { "source": "RUDATA_QUOTES", "status": "SUCCEEDED", "recordsWritten": 1840 },
    { "source": "CBONDS_NAV", "status": "EMPTY", "recordsWritten": 0 }
  ],
  "turnover": { "calcId": "tcj-...", "status": "SUCCEEDED" },
  "finishedAt": "2026-10-20T08:41:12Z"
}
```

Это закрывает претензию «информации об успешной/неуспешной загрузке не получаем».

### События (Kafka / Artemis — Digital Q.MessageBroker)

| Событие | Когда | Кто слушает |
|---|---|---|
| `QuoteLoadJobAccepted` | заявка создана | мониторинг |
| `SourceTaskCompleted` | загрузчик закрыл задачу | оркестратор (join) |
| `QuotesReady` | барьер закрыт без FAILED | постановщик расчета обращаемости |
| `QuoteLoadFailed` | обязательный источник FAILED | алерт, UI, повтор |
| `TurnoverReady` | расчет закончен | справочник ФИ, позиционный контур, UI статуса |
| `TurnoverFailed` | расчет упал при готовых котировках | алерт, повтор только расчета |

Если снаружи уже есть BPM, который сегодня вызывает два метода подряд, процесс переписывается так: одна задача «создать job», затем wait-message на `TurnoverReady` / `QuoteLoadFailed` с тем же `correlationId`. Это правильная «последовательность», в отличие от двух fire-and-forget.

## 10. Ошибки, пусто, ретраи

| Ситуация | Поведение |
|---|---|
| Источник вернул пустой период | `EMPTY`, барьер может закрыться, расчет идет |
| Источник 5xx / таймаут | ретраи с backoff внутри SourceTask, job остается `RUNNING` |
| Ретраи исчерпаны | `FAILED`, расчет **не** стартует, алерт |
| Бумага не найдена в источнике | `NOT_FOUND`; если источник обязательный — `FAILED` + проверка маршрута |
| Один из двух обязательных FAILED, второй SUCCEEDED | job `FAILED`, частичный расчет по умолчанию **не** делаем: иначе статус обращаемости выглядит актуальным при дырявых котировках |
| Повтор `initialPositionLoad` на ту же ФИ и период | возвращаем существующий `jobId`, не создаем второе задание |
| Котировки догрузились после FAILED | новый job (ручной replay или автоповтор), затем расчет |
| Watchdog SLA | алерт, расчет сам по себе не запускается |

Частичный расчет (`PARTIAL`) сознательно вынесен из MVP. Его можно включить позже флагом, но тогда в статусе ФИ должна быть явная пометка «считано по неполным котировкам». Иначе получим тихий ложный READY.

## 11. Как это садится на текущие вызовы

Сегодня, по смыслу переписки:

```text
добавление ФИ
  → initialPositionLoad(quotes)
  → (пауза / сразу следующий вызов)
  → расчет обращаемости
```

Целевое:

```text
добавление ФИ
  → POST quote-load-jobs   // фасад над initialPositionLoad
       internally:
         SourceTask(s)
         wait join
         TurnoverCalcJob
  → вызывающий ждет TurnoverReady или читает GET job
```

Ежедневный контур, который Константин описывал («по каждой ФИ каждый день запрашиваются котировки, и через какое-то время считается обращаемость»), перестает быть отдельной схемой. Планировщик просто создает пачку `DAILY` job. «Через какое-то время» заменяется барьером.

## 12. Наблюдаемость

Без этого решение снова превратится в паузу.

1. Протокол загрузчика уже умеет сохранять исходный ответ источника — привязать его к `task_id`.
2. Метрики: число job в `RUNNING` дольше SLA; доля `EMPTY` vs `FAILED`; время от `ACCEPTED` до `QuotesReady` и до `COMPLETED` в разрезе источника и mode.
3. В карточке ФИ: «котировки: загружены 1840 точек RuData, СЧА: пусто, обращаемость: посчитана, job qlj-…».
4. Алерт на `QuoteLoadFailed` и на stale `RUNNING`.

## 13. Этапы внедрения

Не календарь, а последовательность, чтобы можно было поставлять по частям.

**Этап 1. Завершаемость загрузчиков.** RuData и Cbonds после последней страницы пишут терминальный статус задачи. Без этого оркестратор строить незачем. Проверка: интеграционный тест «3 страницы Cbonds → статус SUCCEEDED только после третьей».

**Этап 2. Реестр job + маршрутизация + join.** `initialPositionLoad` создает job и дочерние задачи. API статуса. Событие `QuotesReady`. Пока расчет по событию можно вызывать руками / старым методом — уже будет видно, *когда* стрелять.

**Этап 3. Автопостановка расчета.** Подписчик `QuotesReady` создает `TurnoverCalcJob`. Внешний последовательный вызов двух методов убирается. `GET job` отдает оба статуса.

**Этап 4. Ежедневный цикл на тот же движок.** Пауза после массовой загрузки дня удаляется.

**Этап 5.** UI статуса на ФИ, replay кнопкой, метрики SLA.

Минимальный полезный срез для сценария входящего перевода: этапы 1–3.

## 14. Что сознательно не делаем

- Не ищем «окончание загрузки всех котировок». Его нет и не будет.
- Не делаем готовность по покрытию календаря торгов («набралось 80% дат — можно считать»). Пока источник не сказал EMPTY или SUCCEEDED, дыра в датах неотличима от незавершенной пагинации. Покрытие — проверка качества *после* барьера, не сигнал барьера.
- Не держим HTTP открытым до конца истории.
- Не запускаем расчет по таймеру «если вдруг загрузчики забыли отозваться».

## 15. Открытые точки — зафиксированные по умолчанию

Их можно пересмотреть, но чтобы спецификация не двоилась, здесь уже выбран вариант.

1. Российский пай: оба источника обязательны (`RUDATA_QUOTES` + `CBONDS_NAV`), пока маршрут не сузят в справочнике.
2. `EMPTY` не блокирует расчет.
3. `FAILED` обязательного источника блокирует расчет.
4. `initialPositionLoad` остается именем фасада, внутри — `QuoteLoadJob`.
5. Идемпотентность на `(instrument, mode, from, to)`.
6. Брокер сообщений — тот, что уже выбран в MDM (Kafka или Artemis).

## 16. Почему это закрывает переписку

| Тезис из диалога | Как закрывается |
|---|---|
| «Механизма окончания загрузки котировок нет» | Появляется, но на гранулярности задания, не системы |
| «initialPositionLoad только для стартовой позиции, дальше каждый день» | Один движок, два mode |
| «Бумага появляется в течение дня, оба метода вызываются последовательно» | Снаружи одна команда, последовательность внутри оркестратора |
| «Нужна история с даты размещения» | `INITIAL_HISTORY`, барьер ждет последнюю страницу |
| «Нет гарантии, что обращаемость загрузится, нет success/fail» | `jobId` + терминальный статус + `TurnoverReady` / `QuoteLoadFailed` |
| «Два источника: RuData и Cbonds / СЧА паев» | Join по обязательным SourceTask |

## 17. Рекомендация одной фразой

Ввести в Управление рыночными данными заявку на загрузку котировок с явным завершением каждого источника и автоматически ставить расчет обращаемости по событию готовности этой заявки. Паузу между двумя методами убрать: она маскирует отсутствие контракта у загрузчиков.
